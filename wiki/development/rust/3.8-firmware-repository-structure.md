# 3.8. Структура репозиторію прошивки

[До змісту](../../../README.md#зміст)

Структура репозиторію має підказувати розробнику, де шукати відповідальність і які файли змінювати для типової задачі. Почни з одного крейта для однієї прошивки й однієї плати. Додавай межу модуля, крейта або пакета, коли вона захищає контракт, обмежує залежності чи дає змогу незалежно зібрати потрібний результат. [Написання коду прошивки](3.7-firmware-code.md)

## 3.8.1. Одна прошивка для однієї плати

Для вузла з датчиком SHTC3 і телеметрією достатньо одного пакета з бінарним крейтом. У `main.rs` ініціалізуй плату, підключи реалізації шини й мережі та запусти роботу застосунку. Тримай розподіл виводів і контролерів у модулі плати, а команди датчика та формат телеметрії — у модулях, яким належать ці контракти. [Cargo Book про бінарні цілі](https://doc.rust-lang.org/cargo/reference/cargo-targets.html#binaries), [Апаратні межі плати](../../1-hardware-platforms.md#113-межі-для-розробника)

```text
Cargo.toml
src/
  main.rs             # Ініціалізація й підключення компонентів
  board.rs            # Виводи, контролери та периферія плати
  drivers.rs          # Оголошення модулів драйверів
  drivers/
    shtc3.rs          # Команди й відповіді датчика
  sampling.rs         # Період опитування й результат вимірювання
  telemetry.rs        # Формат повідомлення й передавання через адаптер
  wifi.rs             # Реалізація мережевого передавання для плати
```

Напрям залежностей видно з імпортів і аргументів. `main.rs` підключає модулі, `board.rs` і `wifi.rs` використовують платформні бібліотеки, драйвер приймає I²C через трейт. Для передавання телеметрії `main.rs` під’єднує реалізацію мережевого інтерфейсу до модуля телеметрії. Сам модуль задає, що означає успішне передавання. [Модулі в Rust](https://doc.rust-lang.org/book/ch07-02-defining-modules-to-control-scope-and-privacy.html), [Межа `embedded-hal`](3.3-peripherals-embedded-hal.md#332-де-використовувати-embedded-hal)

## 3.8.2. Коли виділяти модуль або крейт

| Ситуація | Якої межі достатньо | Що має виграти проєкт |
| --- | --- | --- |
| Пов’язані операції мають одну відповідальність і спільні правила. | Один модуль в одному файлі. | Усі зміни правил залишаються поруч. Наприклад, кодек формує поля повідомлення й перевіряє місткість буфера в `telemetry.rs`. |
| Усередині однієї відповідальності є частини з власними правилами. | Модуль може займати кілька файлів. Тримай реалізацію за вузьким інтерфейсом модуля. | Модуль телеметрії може тримати кодування й планування відправок у різних приватних підмодулях. Викликач використовує інтерфейс телеметрії. [Вибір файлів модулів у Rust](https://doc.rust-lang.org/book/ch07-05-separating-modules-into-different-files.html), [Видимість у Rust](https://doc.rust-lang.org/reference/visibility-and-privacy.html) |
| Кодек треба перевіряти на комп’ютері. Залежності пакета допускають таку збірку. | Бібліотечний крейт у тому самому пакеті може бути достатнім. | Бінарний крейт використовує публічний API `src/lib.rs`, а тести бібліотеки можна збирати під ціль комп’ютера. Перевір, що залежності від плати обмежені відповідною цільовою конфігурацією. [Цілі Cargo](https://doc.rust-lang.org/cargo/reference/cargo-targets.html), [Платформні залежності в Cargo](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#platform-specific-dependencies) |
| Формат потрібен прошивці й окремій утиліті приймання. Проєкту важливо перевіряти кодек без залежності від HAL. | Окремий бібліотечний пакет із власним маніфестом і тестами. Якщо ці пакети належать одному репозиторію й розвиваються разом, об’єднай їх у Cargo workspace. | Прошивка та утиліта використовують один формат. Підтримку `no_std` і граф залежностей кодека можна перевіряти незалежно від апаратних пакетів. [Cargo Book про workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html), [Граф залежностей у Cargo](https://doc.rust-lang.org/cargo/commands/cargo-tree.html) |

Коли додаєш іншу плату, спочатку визнач, що змінюється саме в ній. Якщо достатньо іншої конфігурації ресурсів і адаптера, це може бути другим модулем плати в наявній прошивці. Якщо плати потребують різних SDK, сценаріїв компонування чи окремих релізних образів, розглянь окремі бінарні цілі або пакети. Обирай окремий пакет, коли цілі потрібно ізолювати за залежностями чи процедурою збірки. [Бінарні цілі Cargo](https://doc.rust-lang.org/cargo/reference/cargo-targets.html#binaries), [Підтримка плат у Rust](3.5-platform-support.md)

## 3.8.3. Репозиторій із кількома пакетами

У цьому прикладі кодек став спільним для прошивки й утиліти, яка декодує повідомлення на комп’ютері. Тепер окремий пакет володіє форматом повідомлення, а обидва виконувані пакети залежать від нього. Кодек отримує потрібні поля запису через свій API й може збиратися для мікроконтролера з `no_std`. [Середовище виконання та `no_std`](3.2-runtime-no-std.md), [Cargo Book про workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html)

```text
Cargo.toml                 # Workspace і пакети
Cargo.lock
firmware/
  Cargo.toml
  src/
    main.rs
    board.rs
    telemetry.rs           # Передавання та виклики кодека
telemetry-format/
  Cargo.toml
  src/lib.rs               # Спільний формат повідомлення
  tests/wire_format.rs
telemetry-receiver/
  Cargo.toml
  src/main.rs              # Приймання й декодування на комп’ютері
```

У дереві показані файли, що визначають нову межу. Для прошивки й утиліти задай окремі команди з явним вибором пакета, цілі компіляції та потрібних Cargo features. Для перевірки кодека в CI запусти тести на комп’ютері й збери його в складі прошивки під ціль мікроконтролера. Спільний `Cargo.lock` фіксує набір версій у workspace. [Cargo Book про workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html), [Cargo Book про `cargo test`](https://doc.rust-lang.org/cargo/commands/cargo-test.html), [Відтворювана збірка](3.6-build-flash-debug.md#362-відтворювана-збірка-й-прошивання)

## 3.8.4. Очікувані зміни та перевірки

| Типова зміна | Де очікувати diff | Що перевіряти |
| --- | --- | --- |
| Додати зчитану вологість до телеметрії. | `telemetry.rs` або `telemetry-format`, тести формату й приймач, якщо його контракт змінився. | Точні байти й сумісність із версіями приймача, які проєкт продовжує підтримувати. |
| Замінити SHTC3. | `drivers/`, підключення драйвера в `main.rs` або модулі плати та відповідні тести. | Команди на шині, перетворення одиниць і сценарій вимірювання на платі. |
| Перенести вузол з ESP32-C3 на Pico W. | Модуль плати, мережевий адаптер, цільова конфігурація та спосіб прошивання. | Наявність потрібного режиму I²C і мережевої бібліотеки для Pico W. Збірку, прошивання й надсилання повідомлення від справжнього датчика. [Перевірка підтримки плат](3.5-platform-support.md), [Вибір інструментів прошивання](3.6-build-flash-debug.md#361-вибір-інструментів) |

Закріпи в CI межу, яка забезпечує переносність кодека. Наприклад, перевіряй граф через `cargo tree -p telemetry-format --target <target>` окремо для комп’ютера й мікроконтролера з відповідними Cargo features. Якщо в графі кодека з’явиться HAL або SDK, перевірка має завершитися помилкою. Зміни до правила чи маніфесту кодека тоді будуть видимі на рев’ю. [Cargo Book про `cargo tree`](https://doc.rust-lang.org/cargo/commands/cargo-tree.html), [Межі для розробника](3.1-development-environment.md#314-межі-для-розробника)

Зафіксуй у README проєкту команди, підтримувані плати й коротку навігацію. Правила формату, ініціалізації або використання ресурсу тримай поруч із модулем, якому вони належать.
