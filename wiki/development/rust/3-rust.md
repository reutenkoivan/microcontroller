# 3. Rust для мікроконтролерів

[До змісту](../../../README.md#зміст)

Архітектор обирає мову разом із цільовою платформою, драйверами, моделлю виконання й процедурою випуску. Почни зі сценарію, який може змінити вибір. Це може бути доступ до конкретного режиму периферії, дедлайн обробки, обсяг RAM або сумісність із наявним SDK. [Апаратні платформи](../../1-hardware-platforms.md), [Вимоги реального часу](../../2-rtos.md#22-види-вимог-реального-часу)

## Коли обирати Rust, C/C++ або змішаний стек

Модель володіння Rust дає змогу закласти правила доступу до пам’яті й ресурсів у типи та перевіряти їх під час компіляції. Наприклад, HAL може видати єдиний об’єкт таймера, а модуль плати передати його задачі, яка ним керує. Потрібні режими периферії, ресурси й дедлайни підтвердь окремо на цільовій платформі. [Rust Book про володіння](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html), [Володіння периферією в Embedded Rust](https://docs.rust-embedded.org/book/peripherals/singletons.html)

| Варіант | Коли обирати | Приклад |
| --- | --- | --- |
| **Rust** | Є ціль компіляції, підтримка потрібних операцій у HAL чи SDK і робочий шлях прошивання та налагодження. Володіння ресурсами, типізовані стани або переносні драйвери допомагають закріпити важливі правила проєкту. | У новій прошивці на `embassy-stm32` одна задача володіє I²C, а драйвер датчика працює через трейт `embedded-hal`. [Підтримка платформ](3.5-platform-support.md), [Межа `embedded-hal`](3.3-peripherals-embedded-hal.md#332-де-використовувати-embedded-hal) |
| **C/C++** | Залишай наявний стек, якщо він покриває вимоги, а користь від переходу менша за витрати на повторну перевірку драйверів, таймінгів і процедури випуску. Для нового проєкту обирай C/C++, якщо вирішальний компонент перевірено у SDK виробника, а підтримка його в Rust потребує окремого портування. | Для серійного контролера з перевіреним драйвером таймера, АЦП і DMA додавання каналу вимірювання можна виконати в наявному стеку й повторити тести відповідного тракту. [Периферія та інструменти STM32](../../1-hardware-platforms.md#13-stm32) |
| **Rust разом із C/C++** | Новий модуль дає користь від Rust, а проєкт може зберегти перевірений SDK, драйвер або код на C/C++. Зафіксуй вузький інтерфейс між мовами через FFI (Foreign Function Interface) з погодженим бінарним інтерфейсом C (ABI). | На ESP32 логіка застосунку може бути на Rust, а доступ до сервісів ESP-IDF іти через Rust-обгортки над SDK. [Rust для ESP-IDF](https://github.com/esp-rs/esp-idf), [Rustonomicon про FFI](https://doc.rust-lang.org/nomicon/ffi.html) |

## Перевірка перед вибором

1. **Звір ціль і повний стек.** Перевір точний чип і ревізію плати, підтримку цілі компіляції, вибір `std` чи `no_std`, потрібні режими HAL або SDK, модель переривань і драйвери. Для змішаного стека визнач, яка частина запускає прошивку, і перевір компонування обох частин під ту саму ціль. [Цілі Rust](https://doc.rust-lang.org/rustc/platform-support.html), [Середовище виконання та `no_std`](3.2-runtime-no-std.md), [Переривання, асинхронність та Embassy](3.4-interrupts-async-embassy.md)
2. **Відтвори критичний сценарій на платі.** Збери релізний образ, проший його та перевір потрібний режим периферії, обробку помилки, використання Flash і RAM та затримку за заданого навантаження. Якщо замінюєш наявну реалізацію, повтори той самий сценарій на поточній прошивці. Для FFI перевір також граничні розміри буферів, передавання помилок і контекст, у якому виконуються зворотні виклики. [Перевірка архітектурних рішень](3.1-development-environment.md#316-перевірка-й-фіксація-рішення), [Збірка, прошивання й налагодження](3.6-build-flash-debug.md), [Rustonomicon про FFI](https://doc.rust-lang.org/nomicon/ffi.html)
3. **Перевір шлях супроводу.** Відтвори збірку зі свіжого клону, під’єднай налагоджувач, знайди причину збою за журналом або символами та перевір процедуру оновлення інструментарію чи SDK. Для переходу з C/C++ оціни, які драйвери, інтеграції й перевірки доведеться перенести або підтвердити повторно. [Відтворюване середовище розробки](3.1-development-environment.md#315-відтворюване-середовище-розробки), [Відтворювана збірка й прошивання](3.6-build-flash-debug.md#362-відтворювана-збірка-й-прошивання)

## Межі для розробника

Зафіксуй, де міститься прикладна логіка, хто володіє периферією та як розробник робить типову зміну через готовий інтерфейс і команду збірки. Заклади правила у типи, межі модулів і конфігурацію проєкту. [Загальні межі для розробника](3.1-development-environment.md#314-межі-для-розробника)

| Що фіксує архітектор | Штатна дія розробника | Де видно відхилення |
| --- | --- | --- |
| **У Rust.** Безпечні API для логіки та драйверів, власник кожного ресурсу й модулі, де обґрунтовано використовують `unsafe`. | Передає ресурс через погоджений тип і викликає готовий API. Для нового низькорівневого доступу документує умови, від яких залежить його коректність. | Порушення правил володіння виявляє компілятор. Новий `unsafe` або імпорт апаратного крейта в логіці застосунку видно на рев’ю. [Rust Book про `unsafe`](https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html), [Володіння периферією](https://docs.rust-embedded.org/book/peripherals/singletons.html) |
| **У C/C++.** Контракти володіння й часу життя буферів, межі доступу з переривань, погоджені налаштування компілятора та перевірки для цільової збірки. | Використовує готові інтерфейси драйверів і запускає погоджені перевірки коду та сценарії на стенді. | Зміни розміру буфера, правил його передавання, параметрів компіляції чи доступу з переривання привертають увагу на рев’ю. [Переривання й спільні ресурси](3.4-interrupts-async-embassy.md#343-межі-для-розробника), [Межі збірки й діагностики](3.6-build-flash-debug.md#364-межі-для-розробника) |
| **На межі FFI.** Визначений адаптер між мовами, погоджені типи й виклики, власник пам’яті, контекст зворотних викликів і спосіб передавання помилок. | Викликає адаптер. Операцію з буфером виконує за контрактом, який задає його розмір, час життя та сторону, відповідальну за звільнення. | Зміна заголовка C, розміщення полів структури, зворотного виклику або коду звільнення пам’яті потребує інтеграційної перевірки на цілі. [Rustonomicon про FFI](https://doc.rust-lang.org/nomicon/ffi.html), [Rust Reference про `repr(C)`](https://doc.rust-lang.org/reference/type-layout.html#the-c-representation) |

**Очікувані файли на рев’ю.** Зміна поля телеметрії зазвичай зачіпає кодек і тести. Якщо diff також змінює заголовок FFI, `build.rs` або додає `unsafe` у прикладному модулі, з’ясуй, яка вимога потребує зміни цієї межі та яку цільову перевірку потрібно повторити.

Запиши обрану мову для кожної частини прошивки, підтверджену конфігурацію плати, результати перевірок і умову, за якої рішення потрібно переглянути.
